# HALMark v0.9.17-draft — November 2026 Release Notes

One new Candidate Footgun, the state-condition `for:` restriction deferred from v0.9.16-draft. Every claim was checked against HA core source and the current HA docs.

## New Footguns

| FG | Title | Severity | Arena |
|---|---|---|---|
| FG-57 | State Condition `for:` Combined With `attribute` or a Helper Entity as the State | hard_fail | 2 |

**FG-57.** Since HA 2026.10, a state condition rejects `for:` together with `attribute:`, or with an `input_*` helper entity as the state. The automation or script is disabled at load and shows as unavailable. Before 2026.10 the same YAML loads but is silently wrong: `for:` is measured from the entity's `last_changed`, which only moves when the main state changes. The correct forms move the duration to a state or template trigger, or put `for:` on a template binary sensor that holds the comparison. The state *trigger* is not affected.

## Verification

- **Schema:** `helpers/config_validation.py`, `STATE_CONDITION_SCHEMA`. In 2026.10.0 and 2026.11.0 it raises "Cannot use 'for' with an attribute" and "Cannot use 'for' with a state referencing an entity". Neither check exists in 2026.9.0.
- **Origin:** HA core PR #174083, merged 2026-09-13, labeled breaking-change, first in 2026.10.0. The PR description also names a list of states, but the shipped code and current docs allow a list with `for:`.
- **Pre-2026.10 behavior:** `helpers/condition.py` `state()` (2026.9.0) compares the attribute or helper value but checks the duration against `entity.last_changed`.
- **Load behavior:** `components/automation/config.py` and `entity.py` (2026.11.0) log "… has been disabled: …" and create an `UnavailableAutomationEntity`. Scripts follow the same pattern.
- **Docs:** conditions/state ("Can't be combined with `attribute`, or with a helper entity as the state"), triggers/state (`for:` covers "the new state or new attribute value"), triggers/template (`for:`).
